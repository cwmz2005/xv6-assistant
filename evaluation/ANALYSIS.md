# 开发集检索对比

本报告对应 development.source-verified.jsonl 与 development-retrieval-warm-results.json。共六题，覆盖事实、源码定位、跨文件分析和库外问题。相关片段由开发者读取源码后核对，标注不是独立人工测试集；样本规模小，不能据此推断泛化性能。

所有方案使用相同问题、默认 util 原始版本、E5 模型、Top K=5、候选数=20。模型先预热，随后串行运行。五道库内题参与排序指标，库外题的 Recall、MRR、nDCG 均为 null，不计入均值。延迟统计包含全部六题。

| 方案 | Recall@5 | MRR@5 | nDCG@5 | 平均召回 ms | 平均重排 ms |
|---|---:|---:|---:|---:|---:|
| Dense | 0.600 | 0.367 | 0.426 | 1414 | 0 |
| Hybrid | 0.700 | 0.550 | 0.579 | 739 | 0 |
| Hybrid + Reranker | 0.800 | 0.600 | 0.652 | 823 | 6576 |

这次运行中 Hybrid 的指标高于 Dense，说明标识符、函数名等词面信号对源码定位有帮助。重排序的总体指标进一步提高，但增加约 6.6 秒 CPU 延迟，并非所有题都获益。

跨文件题 cross-fork-copy 中，Hybrid 召回两个已标注相关片段中的一个；重排序后这两个片段均未进入 Top 5。这说明局部文本相关性不等于跨文件证据覆盖，单一 Cross-Encoder 分数可能压低某个必要的证据节点。后续可以评估按文件/函数多样性选取证据，或对跨文件题增加候选预算，不能直接假设重排总是更好。

fact-fork-return 的 Dense 与 Hybrid 均未在 Top 5 命中目标 fork 片段。需要进一步检查中文表述与英文标识符的跨语言匹配、长函数截断和教材相近内容竞争。优化应在训练/开发集上完成，并使用独立测试集验证，避免只针对这六题调参。

延迟只有一次运行，仍受首次数据库缓存、操作系统调度、测试顺序等影响。Dense 比 Hybrid 慢不代表增加 BM25 会加速向量检索；需要多次运行并轮换顺序才能形成性能结论。

回答准确性与库外拒答尚未在本报告中评分。首次生成实验遇到上游读取超时，后改为低推理强度后完成八条回答，保存在 development-generation-results.json。该批次还暴露了部分回答截断、模型缩写引用 ID 导致引用未关联的问题。旧记录保持原样；后续生成已增加完成状态、token 用量、截断提示和唯一短 ID 恢复，但不能将这些改进追溯应用到旧回答来美化实验结果。

开发者检查发现，库外 CUDA 问题的 RAG 回答没有编造 CUDA 调度器，并指出缺少证据；这只是样例检查，尚不是人工拒答准确率。跨文件问题中，完整证据不足时回答仍可能包含依据设计惯例的推测，说明检索不足和证据约束需要分别检查。

人工核验通过 API 或实验面板保存核验人、0–1 评分和说明，未评分记录保持空值。评分前必须检查是否截断、引用是否对应证据、是否混入不同源码版本；不能以检索分数填充准确率。
